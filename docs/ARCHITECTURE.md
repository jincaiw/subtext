## 1. Crate 分层

```
subtext (workspace)
├── subtext-core      纯逻辑，零 UI 依赖
├── subtext-syntax    .cotsyntax 解析 + 高亮规则引擎
├── subtext-theme     .cottheme 解析 + 主题管理
└── subtext-app       GPUI 应用（默认 member，产出 subtext 可执行文件）
```

依赖方向严格单向：`app → {core, syntax, theme}`，三个基础 crate 之间互不依赖。
这样 `subtext-core` 可以在没有窗口系统的情况下跑单元测试。

| Crate | 行数 | 测试 | 职责 |
| --- | --- | --- | --- |

| **合计** | **10,180** | **124** | |

## 3. 命令的生命周期（核心数据流）

这是整个应用最重要的一条链路。一次按键或一次点击，走完这七步：

```
① 用户在菜单点击 / 按下快捷键
        │
        ▼
② GPUI 按 focus path 找到对应 action 类型
   （actions.rs 里 182 个类型之一）
        │
        ▼
③ bridge.rs 的 cx.on_action 收到该类型
        │
        ▼
④ 取 action 类型名的最后一段 → 命令名字符串
   actions::text::ToggleComment  →  "ToggleComment"
        │
        ▼
⑤ bridge::dispatch 找到注册的 Workspace（WeakEntity）
        │
        ▼
⑥ workspace.dispatch("ToggleComment", window, cx)
        │
        ▼
⑦ dispatch.rs 的 match 命中分支 → 调用真正的行为
   text_op(...) → textops::toggle_comment(...) → 写回编辑器
```

**为什么中间要插一层字符串命令名？**

因为菜单表（`resources/menu.json`）本身就是以字符串描述动作的。
让分发键与菜单表的 `action` 列同名，意味着：

- 生成器可以从同一份数据同时产出 `menu.rs` 和 `keymap.rs`；
- 一个菜单项是否「已接线」可以直接用字符串比对来验证（见 §7 的守卫测试）；
- 未实现的命令落到 `other =>` 分支，**在状态栏说明原因**，而不是静默吞掉按键。

第 ⑦ 步的 `dispatch` 是**唯一**决定命令行为的地方。
`bridge` 不判断语义，`menu` 不含逻辑，`keymap` 只有键位。

## 4. 关键设计决策

### 4.1 为什么 `EditorState` 而不是自己写文本引擎

`gpui_kit::base::input::EditorState` 已经提供了行号、软折行、缩进参考线、
代码折叠（`FoldRange`）、诊断下划线、撤销栈。重写这些没有收益。

关键是它开了一个缝：`InputHighlighter` trait。

```rust
pub trait InputHighlighter {
    fn language(&self) -> &str;
    fn update(&mut self, edit: Option<InputEdit>, text: &Rope, window: &mut Window,
              cx: &mut Context<EditorState>);
    fn styles(&self, range: &Range<usize>, resolver: &dyn HighlightStyleResolver) -> Vec<(Range<usize>, HighlightStyle)>;
    fn fold_ranges(&self, text: &Rope) -> Vec<FoldRange>;
}
```

`subtext-app::highlighter::CotHighlighter` 实现它，内部跑的是
`subtext-syntax` 从 `.cotsyntax` 解析出的规则。
**所以 token 颜色与 CotEditor 一致，而不是与 GPUI Kit 的内置高亮器一致。**

### 4.2 为什么 `SyntaxManager` 而不是 `Arc<Vec<Syntax>>`

最初 `Workspace` 存的是 `Arc<Vec<Syntax>>`，因为高亮工厂需要一份 `'static` 的副本。
但这样就没法用 `by_name()` / `syntax_for_path()` / `plain_text()` 这些查找方法。

改为 `SyntaxManager`（内部就是 `Vec<Syntax>`），并新增
`SyntaxManager::from_syntaxes(Vec<Syntax>)` 用于合并内置 + 用户目录
（按名去重、后者覆盖前者、再按名排序）。高亮工厂仍拿 `Arc<Vec<Syntax>>`，
由 `syntaxes.all().to_vec()` 生成，两者互不干扰。

### 4.3 为什么重入要用 `window.defer`

`entity_map.rs:232` 会 panic：

```
cannot update Entity<Workspace> while it is already being updated
```

视图自己的事件 handler 就运行在 `Workspace::update` 内部。
所以 handler 里若再 `cx.update(...)` 同一个 `Workspace`，立即 panic。

`window.defer(cx, move |window, cx| ...)` 把闭包推到当前 update 之后执行，
这是 GPUI 提供的标准解法。

### 4.4 菜单为什么是「生成」的

`menu.rs` 与 `keymap.rs` 文件头都写着：

> Do not edit this file by hand — run the generator instead.

`tools/generate_menu.py`（约 430 行）读 `resources/menu.json`，产出两个文件，
并在文件末尾**自动附上测试守卫**。这样：

- 菜单改动只需改 `menu.json`（或重新从 storyboard 提取）；
- 「菜单项是否有动作」「快捷键是否可解析」变成编译期可验证的事。

生成器处理的三个非平凡问题：

| 问题 | 处理 |
| --- | --- |
| `control` → GPUI 只认 `ctrl` | `MODIFIERS` 映射表 |
| 大写字母键等价于 `shift + 小写` | `physical_key()` 反推 |
| 方向键在 Cocoa 是 `\uf700` | `NAMED_KEYS` 映射到 `up`/`down`/`left`/`right` |
| 13 个 Find 项共用一个 selector | `TEXT_FINDER_ACTIONS` 按标题补回歧义 |

GPUI 的 macOS 后端就是 AppKit 应用，而 AppKit 只给**从带 `Info.plist` 的 bundle
启动**的进程菜单栏、Dock 图标和获取焦点的能力。裸 Mach-O 能跑，但行为像后台进程。

## 6. `Workspace` 结构

```rust
pub struct Workspace {
    pub settings: Settings,              // 全局配置
    syntaxes: SyntaxManager,             // 70 个语法，供查找
    themes: ThemeManager,                // 14 个主题，供查找
    theme: Theme,                        // 当前主题（展开后的颜色表）
    documents: Vec<OpenDocument>,        // 打开的文档
    active: usize,                       // 当前标签下标
    find: FindState,                     // 查找状态（查询、匹配、当前项）
    find_query: Entity<InputState>,      // 查找输入框
    find_replacement: Entity<InputState>,// 替换输入框
    status: Option<Status>,              // 状态栏消息
    loading: bool,                       // 加载中标志（抑制 dirty 标记）
    settings_window: Option<AnyWindowHandle>,
    about_window: Option<AnyWindowHandle>,
}
```

`OpenDocument` 持有 `Entity<EditorState>` 与文件元信息
（路径、编码、BOM、换行符、是否已修改、语法名）。

方法按职责分为 12 组：

| 分组 | 代表方法 |
| --- | --- |
| 文档管理 | `new_document`、`new_tab`、`push_document`、`open_path`、`close_active` |
| 保存 | `save`、`write_to`、`revert` |
| 文本操作 | `text_op`、`surround`、`select_word`、`select_line`、`set_selection` |
| 查找替换 | `show_find`、`find_step`、`find_all`、`replace_all`、`use_selection_for_find` |
| 跳转 | `goto_line`、`goto_dialog` |
| 外观 | `set_theme`、`apply_theme_by_name`、`set_font`、`bump_font`、`set_font_size` |
| 格式 | `set_line_ending`、`change_encoding`、`reinterpret_encoding`、`set_syntax` |
| 选项 | `update_editor_options`、`update_window_options`、`apply_settings` |
| 面板 | `show_sidebar`、`show_inspector`、`toggle_settings`、`show_about` |
| 检查器 | `inspect_selection`、`inspect_document` |
| 渲染 | `render_toolbar`、`render_tab_bar`、`render_sidebar`、`render_inspector`、`render_find_bar`、`render_status_bar` |

### 守卫测试（生成的）

这三条是**把运行期故障前移成编译期失败**的关键：

```rust
// keymap.rs
fn every_binding_parses()              // 构造全部 72 条 KeyBinding，捕获 panic
fn collisions_are_the_ones_we_know_about()
fn the_shortcut_table_matches_the_bindings()  // 显示表与绑定表一致

// menu.rs
fn the_bar_has_every_top_level_menu()  // 28 个顶层菜单都在
fn every_item_has_an_action()          // 每个菜单项都映射到了已声明的动作
```

`every_binding_parses` 的存在理由见 [评估报告 §4.1](EVALUATION.md)：
GPUI 的 `KeyBinding::new` 对无法解析的键位会 `unwrap()` panic，
而这只在**运行时**暴露。有了这条测试，`cargo test` 就能抓住它。

## 8. 跨平台

| 关注点 | 处理方式 |
| --- | --- |
| 窗口系统 | GPUI 的 `gpui-pre-{macos,windows,linux}` 各自实现，业务代码无感 |
| `secondary` 修饰键 | macOS = Command，Windows/Linux = Control（GPUI 内建） |
| 等宽字体 | `dispatch.rs::mono_font()` 按 `#[cfg]` 返回 Menlo / Consolas / DejaVu Sans Mono |
| 平台专属能力 | 拼写、语音、AppleScript 在非 macOS 上提示「不可用」，菜单项保留 |
| 路径 | 一律 `PathBuf`，无字符串拼接 |

## 9. 扩展点

要加一个新命令，只需三步：

1. 在 `actions.rs` 对应命名空间里加一个动作名；
2. 在 `dispatch.rs` 的 match 里加一个分支，调 `workspace.rs` 的新方法；
3. 在 `resources/menu.json` 里加一条记录，重跑 `tools/generate_menu.py`。

`bridge.rs` 的 `bind_actions!` 宏会自动为新动作注册 handler，不需要改。
